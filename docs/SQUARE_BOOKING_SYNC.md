# Square trial calendar sync

Businesses can keep their Square booking link and work in Square while evaluating Solutionist. This is an explicit owner opt-in, one-way, read-only calendar copy, not a migration. No new Square scopes are required. The feature never writes native bookings, sessions, contacts, invoices, messages or marketing consent. Copies do not change public booking availability. Customer names and service names are not imported with the current scopes. Keep all customer booking links and reminders in Square throughout the trial.

## Operation

GET /square/bookings/sync returns safe status and copied appointments. PUT takes connection_id, selection_revision and enabled (a strict boolean). POST requests a due sync; it cannot bypass the 15-minute cooldown or another worker lease. All endpoints require authenticated current ownership and the pilot allowlist. Reads recheck connection generation and ownership; writes recheck ownership under a database lock.

A leader-gated scheduler checks each minute, processes at most five due accounts concurrently, and reads selected active locations using <=31-day windows. The complete rolling window includes the previous seven UTC calendar days and the next 86 days. Limits: 5,000 appointments, 100 booking requests and 120 seconds per account. A database lease lasts three minutes and survives process restarts. Every successful or handled failed attempt schedules a retry in 15 minutes. Status reports an error code and marks copies stale after 30 minutes without success. Full pagination is required before replacing the snapshot. Partial reads, timeouts, throttling and failures retain the last complete copy. A lower booking version never replaces a newer stored version. Complete snapshots remove appointments moved outside the selected locations/window and reflect cancellations/no-shows without treating them as paid/completed sessions.

Changing saved locations, disconnecting, stopping sync or transferring business ownership removes the copies and invalidates in-flight work atomically. New ownership and new location selections require fresh opt-in. Business deletion cascades through square_connections. The temporary mirror is excluded from portable account exports; it can be reconstructed only by reconnecting and opting in. Database tables/RPCs are service-only with RLS and no browser grants. No provider payloads or secrets are logged. There is no unsigned webhook endpoint: scheduled reconciliation supplies automatic updates, with up to approximately 15 minutes of lag. Webhooks can be added later if faster updates are needed.

## Rollout and rollback

1. Apply supabase/APPLY-2026-10-11-square-booking-sync.sql after the two existing Square migrations. It is additive and replay-tested. No automatic startup migration runs.
2. Configure BOTH Railway services: kmj-intake-server (PROCESS_ROLE=web) and kmj-intake-worker (PROCESS_ROLE=worker). The worker needs the same Square environment, app credentials, encryption key, callback/app URLs, owner allowlist and rollout switches. Prefer Railway references to the web service so they stay consistent. When adding production credentials later, add the corresponding worker references too. Deploy backend and frontend, keeping SQUARE_ENVIRONMENT=sandbox and the existing owner allowlist. Set SQUARE_BOOKING_SYNC_ENABLED=true only after the schema is verified.
3. In the sandbox owner's Integrations panel, enable automatic sync. Verify first sync, scheduled refresh, Square changes/cancellation, calendar display, stopping sync, disconnect and ownership/selection race checks.
4. Leave SQUARE_PRODUCTION_PILOT_APPROVED=false until the consenting real-business pilot is coordinated. Production additionally needs environment-specific credentials and the correct registered redirect URI. Public rollout is never implied: SQUARE_PILOT_OWNER_IDS must contain valid owner UUIDs and cannot be empty or wildcarded. Production refuses sandbox application IDs.
5. When a seller agrees, configure the production pilot for that owner, review consent and confirm actual Square Dashboard revocation, availability of their locations/bookings, timezone and cancellation behavior. No live business has been recruited in this implementation.

Rollback: SQUARE_BOOKING_SYNC_ENABLED=false stops workers and hides copied appointments without touching Square. A business can stop sync to delete copies. Restore sandbox environment/production approval false if a production check fails. Do not rotate the encryption key during rollback; that would invalidate existing credentials.

## Security evidence

Automated tests cover authenticated owner gates, non-pilot denial, browser-bound one-use OAuth state and callback replay, duplicate merchant isolation, encryption/redaction, failed revocation retry, opt-in strictness, kill switches, cross-environment keys, lease contention/expiry, late completion after removal, ownership transfer, selection changes, lower booking versions, cancellation, partial reads and storage denial for anon/authenticated roles. See test_square_connect.py, test_square_booking_preview.py, test_square_booking_sync.py, square_connections_db.mjs and square_booking_sync_db.mjs. These are automated checks; they do not substitute for a real seller pilot or a claim of third-party security certification.

Official contracts: [List bookings](https://developer.squareup.com/reference/square/bookings-api/list-bookings), [OAuth](https://developer.squareup.com/docs/oauth-api/overview), [booking event visibility](https://developer.squareup.com/docs/bookings-api/use-webhooks).
